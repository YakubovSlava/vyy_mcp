Skill file structure

What a skill looks like on disk

Every skill is a folder under the shared tools directory (shown on the "⚙" dialog in the Skills tab):

{{ shared_dir }}/tools/ <skill-name>/ manifest.json <module>.py (the entrypoint module manifest.json points to) ... any other files the module imports

manifest.json

{
  "name": "echo",
  "version": "1.0.0",
  "description": "Echoes the given text back",
  "entrypoint": "tool:echo",
  "parameters": { "type": "object", "properties": { "text": { "type": "string" } } }
}
  • name — unique slug ([a-z0-9][a-z0-9_-]+), also the MCP tool name.
  • entrypoint — "<module>:<function>"; <module>.py must exist at the skill's root and define <function> as a top-level function.
  • parameters — optional, documentation only. The real MCP input schema is inferred from the function's Python type hints.

The entrypoint module

# tool.py
def echo(text: str, shout: bool = False) -> str:
    return text.upper() if shout else text

Two ways to install a skill

  • Upload a .zip via "+" on the Skills tab — the zip's root must contain manifest.json and the entrypoint module, same layout as above.
  • Drop the folder directly into {{ shared_dir }}/tools/<skill-name>/ on disk — no upload needed, this works identically.

How fast changes show up

  • The Skills tab reads the directory fresh on every page load — changes are visible immediately on refresh.
  • The MCP server (what real agents/users call) re-scans the directory every 5 seconds and registers/unregisters tools automatically — no restart needed, whether the change came from the "+" upload or from editing files on disk directly.

Validation on install is structural only (valid zip/folder, manifest fields, module parses, function exists) — code is not executed during validation, only when a client actually calls the tool.

Returning multiple files for a human to run themselves

A skill can return more than just a string — any JSON-serializable value gets sent straight back in the MCP response. Use this for a skill that should hand back files for the calling human to save and run under their own account, rather than a text answer. The server never runs anything here — same idea as the Bitbucket connection notebook.

from jupyter_mcp_tools.common.skill_results import SkillFile, files_result

def make_setup_files(project_name: str) -> dict:
    return files_result(
        f"Setup files for {project_name}. Save and run these yourself.",
        [
            SkillFile("setup.sh", "#!/bin/bash\necho hi\n", run_hint="bash setup.sh"),
            SkillFile("config.yaml", f"project: {project_name}\n"),
        ],
    )

Response shape: {"message": ..., "files": [{"filename", "content", "run_hint"}, ...]}. A full working example lives in examples/setup_files_tool/.
